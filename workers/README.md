# بات تلگرام روی Cloudflare Workers (v7)

نسخهٔ ورکر همان `bot.js` است؛ نسخهٔ پایتونی بات در `src/bot/` برای اجرای روی
GitHub Actions می‌ماند. این دو مستقل‌اند و می‌توانید فقط یکی را فعال نگه دارید.

## نصب بدون ترمینال (فقط از داشبورد Cloudflare)

نیازی به `wrangler` و `npx` نیست؛ اولین چهار خط راهنمای قبلی همه معادل داشبوردی
دارند:

| کار | معادل داشبورد |
|---|---|
| `wrangler kv namespace create BOT_KV` | Workers & Pages → KV → **Create a namespace** → نام: `freeai-hunter-bot`. اگر Worker را با کد چسبانده (Quick edit) ساخته‌اید، در **Settings → Bindings → Add → KV namespace**، Variable name را `KV` و همین namespace را انتخاب کنید. اگر با روش «Connect to Git / wrangler.toml» deploy می‌کنید، `id` را از صفحهٔ namespace بردارید و در `wrangler.toml` بگذارید. |
| `wrangler secret put X` | Worker → **Settings → Variables and Secrets** → **Add** → نوع **Secret** → نام دقیقاً `X` → مقدار → Save. (در UI، Secret decrypt هم لازم نیست.) |
| `wrangler deploy` | اگر کد را در داشبورد چسبانده‌اید: همان‌جا **Deploy / Save and Deploy**. اگر مخزن را وصل کرده‌اید: با هر push به `main` خودش deploy می‌شود. |
| `curl .../setup` | فقط یک آدرس را در مرورگر باز کنید (بخش بعد). |
| `curl .../diag` | همان آدرس را با `/diag` باز کنید؛ JSON برمی‌گردد. |
| `node --test workers/bot.test.mjs` | لازم نیست محلی اجرا شود: ورک‌فلوی `workers-tests` در GitHub Actions روی هر push تست‌ها را اجرا می‌کند (بخش تست). |

### گام‌به‌گام در داشبورد

1. **ساخت Worker**: Workers & Pages → Create → Workers → نام مثلاً `freeai-bot`.
   اگر از قبل دارید، همان را باز کنید: Workers & Pages → `freeai-bot` → Edit code.
2. محتوای کامل `workers/bot.js` را در ادیتور کدِ داشبورد جای‌گذاری کنید و
   **Deploy** بزنید.
3. **Settings → Bindings → Add → KV namespace**: Variable name = `KV`،
   namespace ساخته‌شده را انتخاب کنید. (`KV` بزرگ و دقیقاً همین؛ کد دنبال
   `env.KV` می‌گردد.)
4. **Settings → Variables and Secrets** این‌ها را به‌عنوان **Secret** اضافه کنید:
   `TELEGRAM_BOT_TOKEN`، `ADMIN_IDS`، `ADMIN_SECRET`، `WEBHOOK_SECRET`،
   `GH_TOKEN` (و اختیاری `GEMINI_API_KEY`، `GROQ_API_KEY`).
   `DATA_REPO` می‌تواند Secret یا Variable معمولی باشد (مقدار `tcpzizi/freeai-data`).
5. **Settings → Trigger Events → Cron Triggers** (اگر می‌خواهید هر ساعت خودکار
   ارسال شود): `0 * * * *`.
6. یک‌بار وبهوک را ثبت کنید: در مرورگر
   `https://freeai-bot.<your-subdomain>.workers.dev/setup?key=<ADMIN_SECRET>`
   را باز کنید. باید `{"ok":true,...}` ببینید. اگر `false` بود، پیام `description`
   تلگرام را بخوانید (معمولاً رمز اشتباه یا توکن نامعتبر).
   - چون کد در URL است، بعد از یک‌بار استفاده یک `ADMIN_SECRET` تازه بگذارید.
   - `https://<worker>/webhookinfo?key=<ADMIN_SECRET>` نشان می‌دهد تلگرام چه URLی
     را ثبت کرده و چند آپدیت در انتظار است.
7. سلامت و آمار: `https://<worker>/health` (باید `ok v7` بدهد) و
   `https://<worker>/diag?key=<ADMIN_SECRET>`.
8. **بدون باز کردن URL هم می‌شود**: در تلگرام به خود بات `/start` بزنید؛ اگر
   وبهوک از قبل روی همین Worker باشد کار می‌کند، ولی برای ثبت یا تغییر وبهوک
   همان گام ۶ لازم است.

### اگر `curl` و ترمینال را ترجیح می‌دهید

```bash
cd workers
npx wrangler kv namespace create BOT_KV        # id را در wrangler.toml بگذارید
npx wrangler secret put TELEGRAM_BOT_TOKEN     # و بقیهٔ secretها
npx wrangler deploy
curl "https://<worker>/setup?key=$ADMIN_SECRET"
```

## سقف‌های پلن رایگان که کد با آن‌ها کار می‌کند

| محدودیت | مقدار | کاری که کد می‌کند |
|---|---|---|
| Subrequest per invocation | ۵۰ | بودجهٔ ۴۵ با ذخیرهٔ چند تا برای تلاش دوباره؛ ۱ پیام به هر کاربر در هر اجرا |
| KV operations per invocation | ۱٬۰۰۰ | بودجهٔ ۹۰۰؛ یک `list` + multi-get برای همهٔ کاربران |
| KV writes per day (کلید متفاوت) | ۱٬۰۰۰ | یک نوشتن به‌ازای هر کاربر تحویل‌گرفته، رأی‌ها ادغام‌شده در یک کلید دقیقه‌ای |
| Worker CPU | ۱۰ ms | سقف واقعی برای رندر HTML؛ کاری سنگین در ورکر نیست |
| Cron duration | ۱۵ min | هر دیسپچ زیر چند ثانیه |

عدد واقعی (اندازه‌گیری‌شده با هارنس تست): ۲۰ کاربر که ۸ آفر گرفته‌اند → ۴۵
عملیات KV، ۲۲ نوشتن، ۲۲ subrequest. برای ۴۰ کاربر → ۷۹ / ۳۶ / ۳۶، و بقیه برای اجرای
بعدی می‌مانند. یعنی سقف واقعی این پلن حدود ۵۰۰–۶۰۰ کاربر است، نه ۱٬۰۰۰ کاربر.

علت ۳٫۲ ثانیه برای ۲۰ کاربر در هارنس: هر کاربر یک آفر تازه می‌گیرد، یعنی یک
fetch صفحه + یک LLM. اگر همه از کش بخوانند، همان ۲۰ کاربر در ~۰٫۶ ثانیه تمام می‌شود.
در ورکر واقعی برای ۵۰۰ کاربر این کار از سقف ۱۰ ms CPU رد نمی‌شود چون زمان انتظار
شبکه حساب نمی‌شود، ولی بهتر است تعداد کاربران را پله‌پله بالا ببرید و `/diag` را ببینید.

## مسیرها

| مسیر | دسترسی | کار |
|---|---|---|
| `POST /tg` | فقط با هدر `x-telegram-bot-api-secret-token` | وبهوک تلگرام |
| `GET /health` | آزاد | پاسخ `ok v7`، هیچ رمزی برنمی‌گرداند |
| `GET /setup?key=` | ادمین | setWebhook + setMyCommands |
| `GET /diag?key=` | ادمین | آفرها، کاربران، بودجهٔ اجرا، آخرین خطا |
| `GET /dispatch?key=[&async=1]` | ادمین | ارسال دستی |
| `GET /errors` `/clearerrors` `/recache` `/raw` `/preview` | ادمین | نگه‌داری و دیباگ |

`ADMIN_SECRET` اگر تنظیم شود اولویت دارد؛ در غیر این صورت `WEBHOOK_SECRET`.
رمزها در `/diag` فقط به‌صورت `true/false` برمی‌گردند، نه مقدار.

## دستورهای بات

کاربر: `/start` `/latest` `/why <id>` `/status` `/settings` `/mute` `/unmute` `/stop` `/help`

ادمین: `/pending` `/users` `/push` `/id` (با ریپلای) `/forget <uid>` `/recache` `/resend`
`/diag` `/errors` `/clearerrors` `/broadcast <متن>`

## تست

نیازی به نصب چیزی روی سیستم خودتان نیست: ورک‌فلوی `workers-tests` در همان
ریپوی GitHub روی هر push که `workers/` را تغییر دهد اجرا می‌شود (تب Actions →
workers-tests). محلی هم اگر Node ۲۲+ دارید:

```bash
node --test workers/bot.test.mjs     # ۲۳ تست، بدون شبکه
```

تست‌ها تلگرام، گیت‌هاب و KV را mock می‌کنند و رفتار را می‌سنجند: تحویل پیام،
پیام سمی که تلگرام رد می‌کند، ۴۲۹، سقف KV، فیلتر آفر مرده، رأی‌های ادغام‌شده،
هم‌زمانی و مسیرهای ادمین.

## تفاوت‌های مهم با v6

فهرست کامل بالای `bot.js` است؛ خلاصهٔ آنچه واقعاً باعث خرابی می‌شد:

1. پیامی که تلگرام با ۴۰۰ رد می‌کرد، در هر اجرا دوباره فرستاده می‌شد و کاربر
   هیچ آفر دیگری نمی‌گرفت. حالا دو تلاش، بعد آن آفر برای همان کاربر کنار
   گذاشته می‌شود و ادمین خبردار می‌شود.
2. `retry_after` در ۴۲۹ نادیده گرفته می‌شد.
3. هر خطا یک کلید KV می‌نوشت؛ یک قطعی تلگرام سهمیهٔ نوشتن روزانه را می‌سوزاند.
4. هزینهٔ KV هر دیسپچ ~۲.۴ بر کاربر بود؛ با سقف ۱٬۰۰۰ عملیات در اجرا، در چند صد
   کاربر وسط حلقه `KV_ERROR` می‌داد. حالا ۳.۲۵ برای هر کاربر و یک نوشتن.
5. دکمهٔ رأی برای هر فشار یک نوشتن داشت و شناسهٔ آفر در ۴۰ کاراکتر بریده می‌شد
   (شناسه تا ۶۰ کاراکتر است) → دو آفر شمارندهٔ مشترک داشتند.
6. `/latest` سهمیه نداشت؛ هر کاربر می‌توانست کل سهمیهٔ LLM رایگان را بسوزاند.
7. `offerId()` وقتی id/لینک نداشت `Math.random()` می‌گذاشت → آفر هر ساعت دوباره
   «تازه» می‌شد و دوباره ارسال می‌شد.
8. وقتی گیت‌هاب ۴۰۳ می‌داد، دیسپچ بی‌صدا هیچ کاری نمی‌کرد؛ حالا نسخهٔ آخر از KV
   استفاده می‌شود.

## نکته‌هایی که روی پلن رایگان باید بدانید

- **KV writes روزانه ۱٬۰۰۰ کلید است.** فرمول: تعداد کاربران × تعداد اجرای روز
  (به‌علاوهٔ رأی‌ها و کش‌ها). ۲۴ اجرا در روز با ۳۰ کاربر حدود ۷۲۰ نوشتن می‌شود؛
  اگر کاربران بیشتر شد، cron را به هر ۲ ساعت ببرید یا پلن paid را بگیرید.
- **KV نهایتاً سازگار است** (تا ~۶۰ ثانیه). برای همین شمارندهٔ آفر ممکن است یک
  بار دوباره ارسال شود؛ تاریخچهٔ هر کاربر منبع حقیقت است، نه کش.
- ورکر به `state.sqlite` و ورک‌فلوی پایتون کاری ندارد؛ فقط `offers.json` را از
  `DATA_REPO` می‌خواند. اگر آن ریپو خصوصی است `GH_TOKEN` با دسترسی read لازم است.
